# UI Design Rules：Magic Admin

> 新页面请先阅读 [`AI-PAGE-DEVELOPMENT.md`](./AI-PAGE-DEVELOPMENT.md)。本文件只保留当前 Admin V2 的长期视觉和交互底线；共享组件实现优先于历史示例。

本文件专门约束 Magic Admin 的页面视觉、布局、间距、组件风格、交互状态和响应式表现。

它不是模块页面设计稿，也不是具体功能 PRD。具体模块的页面结构、字段、流程和业务优先级，以后续模块规划、设计稿或用户最新指令为准。本文件只定义全项目长期稳定的 UI 设计底线。

## 设计目标

- 做现代 AI Agent SaaS Console，不做传统 ERP/OA 后台。
- 默认浅色模式。
- 视觉气质：清爽、专业、克制、可信、可扩展。
- 信息展示要利于扫描、比较和重复操作。
- 页面要像真实工作台，不像营销落地页。
- 所有界面都应服务于用户完成任务，而不是展示装饰效果。

## 参考方向

参考以下产品的后台体验气质，而不是逐像素模仿：

- OpenAI Platform
- Anthropic Console
- Vercel Dashboard
- Linear
- Dify
- Coze

重点学习：

- 清晰的导航层级。
- 克制的中性色背景。
- 有秩序的信息密度。
- 精准的操作反馈。
- 简洁但不空泛的页面结构。

## 参考项目边界

外层 `../shadcn-admin` 是 UI、组件、布局、样式组织和交互模式的只读参考项目。

参考 `../shadcn-admin` 时，优先分析：

- `components/ui/*` 中的 shadcn/ui 封装方式。
- 布局、导航、Header、Sidebar、表单、表格、弹窗、下拉和响应式交互模式。
- Tailwind class 组织、语义化 token 使用、组件拆分和状态表达方式。

参考时必须遵守：

- 禁止修改、格式化、提交、删除、移动、安装依赖或向 `../shadcn-admin` 写入生成文件。
- 不直接照搬其业务模块、示例数据、营销文案、演示路由、Next.js 专属实现或依赖配置。
- 不把 `../shadcn-admin` 作为唯一 UI 标准；本文件、模块规划、实际设计稿和当前 Admin V2 共享组件约定优先。
- 旧项目 `../legacy-admin` 和 `../legacy-admin-analysis` 只用于理解字段、枚举、接口、权限和业务流程；旧 admin 的 UI 形态不作为新 UI 的默认依据。
- 如果参考项目与本文件冲突，以本文件更克制、长期稳定的规则为准。

## 基础视觉原则

- 以内容和操作为核心，装饰让位于可读性。
- 使用统一的 spacing scale，不要凭感觉写随机间距。
- 使用语义化颜色，不要在页面里散落随意色值。
- 所有承载实际页面的源码目录都必须进入 Tailwind `content` 扫描范围；新增 UI 前必须确认对应 class 会生成 CSS，禁止出现“组件写了 class 但样式未生效”的情况。
- 避免大面积高饱和色块。
- 避免过度渐变、发光、玻璃拟态、复杂背景纹理。
- 避免卡片套卡片。
- 避免用过大的标题、留白和 hero 结构包装后台页面。
- 避免页面元素在 hover、loading、内容变化时发生明显跳动。

## 色彩规则

- 默认使用 shadcn/ui 的语义 token 和 Tailwind 设计系统。
- 页面主背景使用接近白色或非常浅的中性色。
- 内容容器使用白色或轻微区分背景的中性色。
- 边框使用低对比中性色，常规边框不应抢夺注意力。
- 主操作色保持稳定，不要每个模块换一套主题色。
- 状态色应语义明确：
  - 成功：绿色系。
  - 警告：黄色或琥珀色系。
  - 错误：红色系。
  - 信息：蓝色系。
  - 中性状态：灰色系。
- 图表颜色要可区分，但保持克制；不要使用彩虹色堆叠。
- 禁止把页面做成单一色系堆叠，例如整页紫色、蓝紫色、棕橙色或深蓝灰。

## 字体与排版

- 使用系统无衬线字体或项目既定字体。
- 字号不随 viewport 宽度缩放。
- 字距保持默认，不使用负字距。
- 后台页面标题应克制，不使用营销页式超大标题。
- 页面标题用于定位当前页面，不承担宣传文案功能。
- 正文、说明、表格、表单标签要有清晰层级。
- 长文本必须有合适行高，避免密不透风。
- 按钮、标签、表头、状态文案必须确保在中英文和长单词下不溢出。

推荐层级：

- 页面标题：20-24px，半粗或粗体。
- 分区标题：16-18px，半粗。
- 卡片标题：14-16px，半粗。
- 正文和表格：13-14px。
- 辅助说明：12-13px。

## 间距系统

- 使用 4px 基础网格。
- 常用间距优先使用 4、8、12、16、20、24、32、40、48。
- 页面外边距：
  - 移动端：16px。
  - 平板：20-24px。
  - 桌面：24-32px。
- 页面主内容区块之间通常使用 24px 或 32px。
- 组件内部间距通常使用 12px、16px 或 20px。
- 表单字段之间通常使用 16px。
- 工具栏内元素间距通常使用 8px 或 12px。
- 不要用大量随机 margin 修补布局。

## 页面布局

- 后台业务页默认使用 `Sidebar + Header + Main Content`。
- 主内容区域应有清晰的页面头部、主要操作区和内容区。
- 页面头部通常包含标题、简短描述和主要操作按钮。
- 路由入口页的页面头部必须优先使用共享 `PageHeader`，标题和描述默认取对应导航项的 `nav.item.*` 与 `nav.desc.*` 文案，禁止在页面内另写一套标题/描述导致菜单、页面标题和空状态口径不一致。
- 业务页面应沿用同组已形成的外层页面壳：`-m-4 px-4 py-6 lg:px-6` 包裹 `PageHeader`，头部后使用 `Separator className="my-4 lg:my-6"` 再进入内容区；新增或迁移页面前必须先参考同组已完成页面的 PageHeader、分割线和内容间距。
- 主要操作按钮放在用户视线容易发现的位置，通常在页面头部右侧或工具栏右侧。
- 列表页优先结构：
  - PageHeader
  - Toolbar / FilterBar
  - DataTable / List
  - Pagination
- 详情页优先结构：
  - PageHeader
  - Summary / Status
  - Tabs 或分区内容
  - 关键操作
- 表单页优先结构：
  - PageHeader
  - 表单主体
  - 固定或明确的提交区域
- 设置页优先结构：
  - 左侧设置导航或分组
  - 右侧表单内容
- 页面不应为了“丰富”而加入无意义的大图、hero、宣传卡片或装饰模块。

## 容器与卡片

- 卡片用于承载明确的一组信息或操作。
- 卡片圆角保持克制，通常不超过 8px，除非 shadcn/ui 默认组件已有约定。
- 卡片阴影应非常轻，优先使用边框和背景层级。
- 不要将整个页面大面积包进一个巨型卡片。
- 不要卡片套卡片；需要层级时用分区、边框、背景或间距区分。
- 卡片内必须有清晰标题、内容和操作关系。
- 空卡片、占位卡片必须有真实用途，不做纯装饰。

## 导航

- Sidebar 应稳定、可扫描，导航项命名简短清晰。
- 创建或调整 Sidebar 菜单时，必须先判断目标用户、使用频率、任务优先级、风险等级和使用场景，再决定排序。
- 菜单排序优先遵循用户直觉和使用频率：高频、核心、入口型能力靠前；低频、危险、应急、系统级能力靠后。
- 同一组菜单不要按接口、数据库、开发顺序或临时添加顺序排列；新增入口后必须重新审视该组整体顺序。
- 当前页面高亮必须明显但克制。
- 一级和二级导航层级要清楚，不要过度嵌套。
- Sidebar 菜单 icon 必须全局唯一：一级、二级、三级之间也不得复用同一个 icon；新增或调整菜单时必须同步检查整棵菜单树。
- Sidebar 展开态一级分区不显示 icon；收起态只显示一级入口 icon。触发收起态一级入口后，Popover 以一级名称作为头部并用分割线和内容分区隔开，二级分组不显示 icon，三级菜单项保留各自 icon。
- Header 用于全局搜索、组织/工作区切换、用户入口、通知等全局操作。
- 面包屑只在层级较深或用户容易迷路时使用。
- 导航不应因为页面内容变化而跳动。

## 按钮

- 主按钮只用于当前页面最重要的动作。
- 次按钮用于常规操作。
- 危险按钮必须使用危险语义，并配合确认。
- 图标按钮必须有 tooltip 或可访问标签。
- 按钮文案使用动词开头，简短明确。
- 同一组操作内按钮高度、间距、对齐必须一致。
- 禁止用大面积彩色按钮堆满工具栏。
- loading 中的按钮必须保持宽度稳定。

## Badge

- Badge 用于状态、范围、来源、角色等短标签，不用于承载长文本。
- Badge 必须使用浅色背景，文本和内部图标必须使用与背景同色系的深色文本色。
- Badge 不使用深色实底、强对比纯色背景或与语义无关的临时颜色。
- 语义色保持克制：成功使用绿色系，警示使用琥珀/黄色系，信息使用蓝色系，中性使用灰色系。
- 页面内不要手写临时 badge 样式；优先使用共享 `Badge` 组件，确有特殊结构时也必须遵守同色系浅底规则。

## Avatar

- 人员、账号、组织成员、部门入口、模型或套餐图标等头像/缩略图场景必须优先使用共享 `Avatar` 组件，不在页面中临时手写 `img + span`、圆形容器或局部首字母函数。
- 人员、账号和组织成员的图片缺失时，fallback 文案统一由 `Avatar` 根据 `name` 或 `fallbackText` 生成，固定显示 1 个可见字符；中文取首字，英文、数字和服务端缩写也只取首字符并转大写。
- 空名称、横杠或无可用字段时，fallback 统一显示 `?`。页面代码不要自行 `slice(0, 2)`、`charAt(0)` 或复制 `getAvatarText` 逻辑。
- 头像图片 URL 统一交给 `Avatar` 做安全判断；业务页面只传 `src`，不要在调用点重复写图片安全正则。非安全 URL 应自动回退到 fallback。
- 人员、账号、组织成员、部门入口、模型和套餐等 Avatar 场景统一使用圆形；模型、套餐等非人物缩略图通过 `fallbackIcon` 提供语义图标，不通过圆角矩形区分类型。
- Avatar 场景统一使用圆形、统一描边、统一中性背景；调用点只能覆盖尺寸和必要字号，不得覆盖 `rounded-*`、`border-*` 或另写背景色来制造局部风格。
- Avatar 尺寸必须稳定，使用明确的 `size-*` class；同一列表或同一控件组内尺寸和字体大小必须一致，避免 hover、加载或图片失败时发生布局跳动。

## 表单

- 配置型、详情型表单页面默认以预览态呈现，不直接进入可编辑表单。
- 用户点击“编辑”后才进入编辑态；编辑态应尽量保持与预览态一致的结构，只将内容区域替换为对应表单控件。
- 编辑态标题不拼接“/ 编辑中”等文本；如需提示状态，在标题右侧使用 Badge 显示“编辑中”。
- 编辑态必须提供明确的保存与取消操作；取消后恢复到最近一次服务端数据或进入编辑前的数据。
- 配置型表单页面的预览态和编辑态应使用一致的卡片与分区结构；同一类设置页之间的布局、行高、label、说明、控件位置和操作区必须保持统一。
- 配置型表单页面的内容卡片应参考 `SectionNavigation + Card/分区容器` 这类克制结构：卡片内分区标题直接服务内容，不额外添加重复页面标题含义的说明，不为了标题区域强行加分割线。
- 配置型、详情型表单的预览态中，开关、布尔值、启停状态、维护状态等状态类字段必须使用 Badge 呈现，不使用纯文本；Badge 颜色必须匹配语义：启用、正常、可用使用成功色，需要关注、维护中、异常风险使用警示色，关闭、停用、未开启使用中性或 outline 样式。
- 配置型表单的编辑态字段行应使用统一的分行列表结构：左侧为 label 和可选短说明，右侧为控件；桌面端左右两列内容必须上下居中对齐。
- 配置型表单的编辑态 label 使用主文本色，说明文案使用辅助文本色；预览态 label 可继续使用辅助文本色，以区分“查看”和“编辑”的信息层级。
- 表单必须有 label，不要只依赖 placeholder。
- label 下方可以补充短说明，用于解释字段影响范围、填写格式或业务后果；说明必须简短，不要替代帮助文档。
- 业务 CRUD Dialog 表单默认参考“应用菜单”的 Dialog form 样板：`DialogContent overflow-visible sm:max-w-2xl`、`form.grid.gap-4`、`DialogFormField(label + tooltip description + FieldError)`、Footer 放在 form 内。除非页面有明确特殊需求，不要临时混用另一套 Dialog 表单布局。
- 文本输入、文本域、搜索框等可输入控件必须提供 placeholder。
- placeholder 必须提示用户应填写什么，并尽量给出真实格式或示例；不要只写“请输入”这类无信息文案。
- placeholder 只用于输入引导，不能替代 label、说明文案或校验错误。
- 数值范围、金额范围、积分范围等范围输入必须合并为一个共享边框和焦点态的范围控件，中间使用 `-` 或等价分隔符表示区间；禁止把最小值和最大值作为两个彼此分离的输入框散落在筛选区中。
- 必填字段要有明确提示。
- 错误提示靠近对应字段。
- 表单说明文案要短，不要把帮助文档塞进页面。
- 复杂表单应分组，避免一屏堆太多字段。
- 编辑和创建页的提交操作位置要稳定。
- 删除、重置、撤销等危险操作必须明确区分。
- 表单控件高度、圆角、边框和焦点态保持一致。
- 日期区间筛选必须使用 shadcn Date Picker 的 Range Picker 组合方式呈现，即 `PopoverTrigger` 作为单一输入触发器、`PopoverContent` 内承载日历范围选择；不能把开始日期和结束日期作为两个独立输入框散落在筛选栏中。移动端 Sheet 内也保持同一控件，只允许宽度改为占满。日期范围、图标选择器这类宽 Popover 必须限制最大宽度在可视窗口内，并通过共享 Popover 的碰撞检测将面板约束在浏览器可视区域内，禁止左侧、右侧或底部被裁出窗口。

## 表格与列表

- 表格用于结构化数据比较，不要用表格展示不适合比较的内容。
- 表头清晰，列名短而准确。
- 单元格内容要可扫描，长内容应截断并提供查看方式。
- 业务 DataTable 必须使用固定列宽策略：每列显式设置 `size`，表格 `minWidth` 至少等于核心列宽总和；当可视区域不足时允许横向滚动，禁止通过压缩列宽导致表头、状态、类型、数字、日期或短标签换行。
- 状态、类型、范围、来源等短标签列必须使用共享 `Badge`，并保持 `whitespace-nowrap`；日期、数字、短枚举文本也必须不换行。长名称、路径、ID、套餐编号等长文本只允许 `truncate`，不要把列挤到多行展示。
- 行操作应靠右或放入统一操作菜单。
- 表格行更多操作必须参考“应用菜单”行操作样板：右侧对齐容器、`Button size="icon" variant="ghost"`、`aria-label`、`MoreHorizontal`、`DropdownMenuContent align="end"`。
- 行操作项使用 `onSelect`，菜单项图标统一 `mr-2 size-4`。
- 菜单内危险操作放在 `DropdownMenuSeparator` 之后，并使用 `text-destructive focus:text-destructive`。
- 批量操作只在用户选择行后出现或激活。
- loading 使用 skeleton 或稳定占位，不要造成表格跳动。
- 空状态应说明当前没有什么，并给出合理下一步动作。
- 分页、筛选、搜索的位置要稳定。
- 搜索/筛选工具栏中的可见控件必须提供可见 label，说明该控件筛选的字段或范围；禁止只依赖 placeholder、Select 当前值或图标来解释控件用途。label 使用小号、辅助色、低噪声样式，并与控件作为一组呈现。
- 筛选入口按钮统一使用 Lucide `Filter` icon；不要在同类入口中混用 `SlidersHorizontal`、`Settings2` 或其他图标。
- 带搜索/筛选的业务列表统一使用共享 `ListFilterPanel`（`src/components/list-filter-panel.tsx`），参考“模型审计日志”筛选区：桌面端所有搜索条件平铺在网格中，**每行 4 个**（窄桌面窗口为 2 个），所有表单控件宽度由网格单元统一撑满（`w-full`），重置按钮固定在最后一列；不再区分“主搜索区 / 高级搜索”。同类页面禁止临时堆叠多行全宽搜索框、写死 `w-[340px]` 之类的固定宽度或另做一套筛选交互。
- 移动端搜索条件统一收起，只显示一个 Lucide `Filter` 图标按钮（不显示可见文本和数值 Badge，必须提供 `aria-label`），点击后打开 `ListFilterPanel` 当前实现的底部 Sheet；面板内编辑草稿，Footer 提供“重置”（仅重置草稿）和“应用”，关闭面板会丢弃未应用的修改。页面级操作（如“新增”）通过 `ListFilterPanel` 的 `actions` 放在入口按钮旁。桌面端不显示该入口。
- 移动端搜索面板统一使用 `ListFilterPanel` 的底部 Sheet（`side="bottom"`，当前实现使用约 85vh 高度）；新页面不得新增另一套筛选面板。旧的 `FilterSheet` 仅保留给尚未迁移的页面维护。
- 当 API 只提供分字段搜索参数而没有统一 `keyword` 参数时，必须把每个字段作为独立的搜索控件（各自带可见 label），分别映射到对应 API 参数；禁止使用“搜索字段 Select + 单一输入框”的合并控件，禁止前端伪造后端不支持的综合搜索。
- 桌面端列表筛选实时生效：文本输入使用短 debounce（通过 `useListQueryParams` 的 `debounceFields` 配置，最多 5 个字段），Select 与时间筛选即时更新，不要为常规列表额外提供独立“搜索”按钮；移动端在面板 Footer 点击“应用”后更新参数。搜索输入有内容时，右侧必须提供清除按钮。
- 业务列表分页器必须参考“应用菜单”分页器样板：左侧显示 `共 {total} 条`，右侧为 `上一页` 按钮、`当前页 / 总页数`、`下一页` 按钮；按钮使用 `size="sm" variant="outline"`，上一页左侧用 `ChevronLeft`，下一页右侧用 `ChevronRight`。禁止同类列表自行改成纯 icon 分页、不同文案结构或不同排版。
- 套餐、订单、租户、代理、审核等平台管理型列表都属于同一类业务列表，必须共享同一套表格、筛选、移动端 Sheet、更多菜单和分页样式；不得因为模块来自旧 admin 的不同页面形态而另起一套卡片、分页器或行操作 UI。旧 admin 只用于确定字段、枚举和 API 参数，不作为新 UI 形态的依据。
- 业务数据表格不得只让表格区域或表格父容器内部纵向滚动；列表内容应按真实高度撑开，由页面主内容区自然滚动，保证页面标题、筛选区、表格和分页在同一滚动上下文中。只有弹窗、抽屉、Popover 或明确固定高度的局部面板才允许内部纵向滚动。
- 简单列表不要强行上复杂表格能力。

## 状态与反馈

每个页面或关键区块必须考虑：

- Loading
- Empty
- Error
- Success
- Disabled
- Permission denied
- Not found

Loading 与骨架屏规则：

- 只有依赖异步或动态数据的页面区块、卡片、表格、列表、详情、表单和框架品牌区域，在数据可渲染前才展示骨架屏；静态结构、静态示例、占位页和不依赖接口结果的内容不使用骨架屏。
- 骨架屏统一使用 `src/components/ui/skeleton.tsx` 的 `Skeleton` 组件；不要在业务代码里临时手写 `animate-pulse` 占位块。
- 骨架屏结构应尽量贴近最终 UI 的布局、尺寸和信息密度，避免加载完成后产生明显布局跳动。
- 骨架屏只表达加载中的结构，不显示默认业务数据、默认品牌、假数据或会被接口结果替换的临时文案。
- 骨架屏颜色、圆角、动画保持统一组件默认样式，业务页面只通过 `className` 控制尺寸和布局。
- 页面标题区域不采用骨架屏：页面标题、描述、标题右侧操作按钮、静态 Badge 等应直接渲染真实 UI，并在按钮层面处理 disabled/loading。
- 搜索、筛选、Tabs、侧边分区导航等静态交互区域不采用骨架屏；即使列表数据首屏加载中，也应保持搜索/筛选控件真实可见，骨架只覆盖表格、列表、统计值、详情内容、分页总数等依赖动态数据的区域。
- 含 Tabs、侧边分区或设置导航的页面，首次无数据加载和切换 Tab/分区触发异步请求时，都只允许替换当前 Tab/分区内依赖动态数据的内容区域为骨架，标题区和 Tabs/导航本身保持真实可操作。
- 应用框架中的异步品牌区域也必须进入骨架态：左上角 Logo、平台名称、副标题或组织/工作区等依赖接口的数据，在接口返回前不得显示默认 Logo、默认名称、假品牌或旧缓存外的占位文案；收起态至少保留 Logo 尺寸骨架，展开态同时保留名称文本骨架。
- 业务列表页首屏 loading 默认使用共享列表数据骨架模式（如 `ListPageSkeleton`）：只覆盖动态数据区域，例如表格表头、表格行和分页总数；标题区、搜索/筛选工具栏不进入骨架。
- 配置页、详情页和表单页首屏 loading 应只覆盖依赖服务端数据的配置值、详情字段、表单默认值或统计区；页面标题、静态分区导航、静态说明和搜索控件不进入骨架。
- 首屏 loading 与后续 fetching 要区分：首次无数据时使用整页骨架；刷新、筛选、翻页或后台重新请求已有数据时，应尽量保留当前页面结构，只在相关按钮、表格或局部区域展示 loading，避免整页闪烁。

反馈规则：

- 保存、提交、上传、删除等异步操作的全局成功与失败提示必须统一使用 `sonner` toast。
- `sonner` 必须统一放在顶部中间：`<Sonner position="top-center" />`。
- `sonner` 使用组件原生样式，不额外覆盖颜色或 `toastOptions` 样式。
- 异步提交成功后给 `toast.success`。
- 异步提交失败后给 `toast.error`，并保留用户已输入内容。
- 表单字段级错误可以保留在对应控件旁；不要用页面内临时 Alert 替代全局操作反馈。
- 危险操作必须二次确认。
- 长任务应展示进度或明确的进行中状态。
- 错误信息要能指导用户下一步，不要只显示“失败了”。

## 弹窗、抽屉与浮层

- Modal 用于需要用户立即决策的任务。
- Drawer 适合侧边编辑、详情预览、不中断上下文的任务。
- Popover 适合轻量选择、菜单、快捷配置。
- Tooltip 只解释短文本或图标，不承载重要业务信息。
- 弹窗和抽屉必须有明确标题、关闭方式和焦点管理。
- 不要把复杂多步骤流程塞进小弹窗。

## Tabs 与分区

- Tabs 用于同一对象下的平级信息切换。
- 不要用 Tabs 代替主要导航。
- Tab 文案简短，数量过多时应重新设计信息架构。
- 当前 Tab 状态要明显。
- 切换 Tab 不应丢失未保存的关键输入，除非有明确提示。

## 图标

- 优先使用 Lucide React。
- 图标大小和线宽保持一致。
- 图标必须服务于识别和操作，不做纯装饰堆叠。
- 常见操作使用用户熟悉的图标，例如新增、编辑、删除、搜索、筛选、下载、复制、刷新。
- 不熟悉或歧义图标必须配合文字或 tooltip。

## 图表

- 图表用于解释趋势、对比、占比和异常，不用于装饰。
- 图表标题、单位、时间范围、空状态必须清楚。
- 坐标轴、legend、tooltip 文字要可读。
- 图表颜色保持克制，同一指标在不同页面应使用一致颜色。
- 不要用 3D 图表、过度动画或难以阅读的渐变。
- 数据为空时展示空状态，而不是空白画布。

## 编辑器与画布类界面

适用于 Prompt 编辑器、JSON 编辑器、代码编辑器、工作流画布等复杂工具界面。

- 工具界面应优先保证可操作空间。
- 工具栏、侧边配置、画布/编辑区之间层级要清楚。
- 画布和编辑器应懒加载。
- 工具栏按钮要稳定，不因内容变化挤压主工作区。
- 配置面板应支持清晰分组和滚动。
- 错误、校验、运行结果应靠近对应上下文展示。

## 响应式规则

- 桌面端优先保证信息扫描效率。
- 移动端优先保证可读性和关键操作可达。
- 小屏下复杂表格可转为列表、卡片列表或横向滚动，但不能破坏数据含义。
- Sidebar 在小屏可折叠为抽屉。
- Header 操作过多时应收纳到菜单。
- 不允许文本、按钮、表格列互相遮挡。
- 固定尺寸元素必须有响应式约束，例如 min/max、flex、grid、overflow 处理。

## 可访问性

- 所有可交互元素必须可键盘访问。
- 图标按钮必须提供 `aria-label` 或 tooltip。
- 表单字段必须有关联 label。
- Modal、Drawer 需要合理焦点管理。
- 错误提示不能只依赖颜色。
- 文本和背景需要足够对比度。
- loading 和 disabled 状态要能被用户理解。

## 文案规则

- 文案简短、明确、专业。
- 操作用动词，例如“创建 Agent”“保存设置”“复制 Key”。
- 错误文案说明原因和下一步。
- 空状态文案说明当前状态和可执行动作。
- 不用大段介绍性文字解释页面功能。
- 中英文混排时保持格式一致，技术名词可保留英文。

## 禁止事项

- 禁止把后台页面做成 landing page。
- 禁止无意义 hero、大标题、宣传口号。
- 禁止卡片套卡片。
- 禁止随机硬编码大量颜色、字号、间距。
- 禁止过度使用渐变、发光、毛玻璃、装饰背景。
- 禁止按钮、表格、标签在状态变化时明显跳动。
- 禁止用图片或装饰图替代真实界面功能。
- 禁止为了显得完整而添加未经规划的业务字段和操作。

## 视觉验收清单

交付页面或组件前，至少自查：

- 页面是否符合现代 SaaS Console，而不是传统后台。
- 页面主任务是否一眼清楚。
- 布局、间距、对齐是否统一。
- 字号层级是否克制且可读。
- 操作按钮是否有主次关系。
- loading、empty、error、success 状态是否完整。
- 危险操作是否有确认。
- 权限不足是否有兜底表现。
- 长文本、长数字、长英文是否不会溢出。
- 移动端和桌面端是否都不遮挡、不重叠。
- 是否引入了不必要的装饰或依赖。
- 是否没有误改 `../shadcn-admin`、`../legacy-admin` 或 `../legacy-admin-analysis`。

## 维护规则

- 本文件只维护项目级 UI 规则。
- 具体模块的页面结构、字段、流程和验收细节应写入模块规划，不要塞进本文件。
- 如果规则只适用于一个页面或一个模块，不应写进本文件。
- 如果规则影响全项目视觉一致性、组件风格、布局方式或可访问性，可以写进本文件。
